# 中关村三小校园智能讲解助手项目说明文档

本项目是一项面向中小学校园真实应用场景设计与开发的人工智能作品，围绕“校园知识如何更高效、更友好、更准确地服务学生”这一问题展开。我们在整理学校校史、办学理念、校区介绍、社团课程、红色教育、校际交流等资料的过程中发现，现有校园信息虽然内容丰富，但大多分散在不同材料中，学生在查找时往往需要逐篇翻阅，理解成本较高，尤其对于低年级学生来说，传统文本材料不够直观，也不够符合他们的表达习惯。因此，我们希望设计一个能够理解自然语言提问、结合校园知识进行回答、并以亲切方式与学生互动的校园智能讲解助手，让学生能够像“和老师或讲解员对话”一样了解学校。

结合第二十一届宋庆龄少年儿童发明奖人工智能（编程）作品的申报要求，本项目将重点放在“利用人工智能技术解决真实问题”的完整过程上，而不是简单展示模型能力。项目的作品定位是“基于大模型与本地知识库检索增强的校园智能讲解系统”。它既不是一个泛化聊天机器人，也不是只做关键词搜索的普通查询工具，而是一套围绕中关村第三小学校园知识服务场景搭建的智能问答与辅助检索系统。项目当前已经实现了基于本地知识库的校史问答主流程、基于 `yt-dlp` 的 B 站视频信息检索与卡片展示、知识库构建与索引管理机制，以及可直接演示的 Gradio 单页交互界面；同时也为后续接入更多多模态能力预留了扩展接口。

从建设目标来看，本项目主要希望解决三个方面的问题。第一，解决校园资料分散、查找效率低的问题。通过将校园相关 Markdown 文档整理为统一知识库，并建立向量索引，可以让学生通过自然语言直接提问，而不需要先知道资料放在哪一篇文章里。第二，解决回答方式不够贴近儿童理解的问题。系统在最终生成回答时，会以温和、耐心、友好的口吻进行表达，使答案更适合小学生阅读和理解。第三，解决校园知识传播方式单一的问题。在文字问答之外，项目还引入了与校园主题相关的视频检索能力，帮助学生从图文之外获得更直观的外部学习线索。

本项目采用“本地知识库 + 检索增强生成 + 可视化交互界面”的整体技术路线。系统入口为仓库根目录下的 [app.py](/home/g203/zhanghaonan/zgc3-ai-assistant/app.py)，启动时会先加载全局配置、初始化日志、创建编排器 `Orchestrator`，再构建 Gradio 单页界面并启动服务。项目整体结构清晰，主要由配置层、编排层、模型适配层、RAG 检索层、缓存层和界面层组成。配置层集中管理 API Key、模型名称、知识库路径、缓存路径以及功能开关；编排层负责把各项能力串联为完整业务流程；模型适配层统一封装 DashScope SDK；RAG 层负责知识切分、向量构建、粗检索、精排和上下文聚合；界面层负责将问答与搜索结果以适合演示的方式展示给用户。这种分层结构使项目在后续扩展时不必推翻现有框架，只需要在相应层新增能力即可。

在知识库建设方面，项目当前已经整理了 6 份校园相关 Markdown 文档，放置于 `rag_data/` 目录下，主题覆盖学校介绍、发展历程、各校区情况、红色教育、社团课程活动、校际交流与跨龄教育等内容。这样的知识组织方式有两个好处：一是内容来源相对集中、可控，能够为回答提供校园真实语境；二是资料结构清晰，适合进一步做程序化处理。为了让大模型能够高效利用这些资料，项目并不是简单把整篇文档交给模型，而是先对 Markdown 内容进行结构化切分。系统会按标题层级识别文档结构，生成层级块，再对块内容做语义分块，同时保留文件级层级树，用于后续从命中片段回溯到更完整的上层章节。这个设计避免了只返回零散句子造成的上下文不完整问题，也让最终回答更加连贯。

在索引构建方面，项目已经具备完整的离线构建链路。系统可读取 `rag_data/` 中的文档，调用文本向量模型生成嵌入，再用 `faiss-cpu` 构建本地向量索引，并同步保存文档元数据与层级树结构。目前仓库中的 `rag_index/` 目录已经存在 `index.faiss`、`documents.json` 和 `file_trees.json` 等文件，说明知识库索引已经实际生成完成，而不是停留在方案阶段。这样，在演示或运行问答时，系统可以直接加载已有索引，进入检索增强问答流程。对于比赛评审而言，这意味着项目已经具备从原始资料整理、知识切分、向量化处理到检索落地的完整实现过程。

本项目目前已经实现的核心功能主要包括三部分。第一部分是校史与校园知识问答功能。用户在前端输入问题后，系统会调用 `Orchestrator.stream_ask_school` 进入主流程，先对问题做向量化，再在 FAISS 中执行 TopK 粗检索，随后调用重排序模型进行精排，最后根据命中的标题路径回溯到更完整的章节级内容，把这些上下文与用户问题一起发送给对话模型，由模型流式生成自然语言回答。第二部分是 B 站视频信息检索功能。用户输入关键词后，系统通过 `yt-dlp` 的 `bilisearch` 能力获取公开视频元数据，只提取标题、链接、封面、时长和发布者等信息，不下载视频内容，再把结果以卡片形式显示在前端，用于辅助校园主题学习与展示。第三部分是缓存与可复用演示能力。系统会对 B 站检索结果做文件级缓存，并通过原子写入方式保证落盘稳定性，从而提升重复查询时的响应效率。

在问答流程的实现上，本项目最有技术特点的部分是层级回溯式 RAG 设计。传统简单问答系统往往只把向量检索到的几段文本直接交给模型，这样虽然实现快速，但容易造成上下文片段化，导致回答缺少完整背景信息。本项目则在粗检索之后引入了基于 `qwen3-rerank` 的精排步骤，并在确定高相关候选后，不直接返回碎片文本，而是根据候选所属的标题路径回溯到文档中更完整的章节内容，再对去重后的章节作为最终参考上下文。这种“细粒度命中、上层聚合返回”的方式，既保留了检索精度，又增强了回答的完整性和可读性，更符合校园讲解场景的需求。

在界面设计方面，项目使用 Gradio 构建单页交互界面，当前已经实现聊天窗口、用户输入框、发送按钮、新对话按钮以及折叠式 B 站搜索区域。前端还支持自定义背景图、主题样式与卡片式展示，使整个应用既适合调试，也适合演示。聊天部分会以流式方式显示模型回答，增强互动感；视频检索部分则用 HTML 卡片把结果集中呈现，便于快速浏览。对于比赛评审来说，这种界面设计能较好地体现项目从算法到应用的完整落地，而不是只有后端逻辑或静态材料。

从实现过程来看，本项目大体经历了以下几个阶段。首先是需求分析阶段，我们从校园实际场景出发，明确了“资料多、入口散、儿童理解门槛高”这一核心问题，并确定作品要服务于学生使用场景，而不是追求复杂的大模型炫技。其次是数据整理阶段，我们将校园校史与办学相关材料整理为结构化 Markdown 文档，形成可持续扩展的知识库底座。然后是知识库建模阶段，完成 Markdown 分层切分、文档树构建、向量化、FAISS 索引与元数据保存。接着是业务编排阶段，搭建 `Orchestrator` 作为统一调度中心，将问答、检索、缓存等能力接入同一套业务流程。最后是界面实现阶段，完成 Gradio 单页 UI 与交互绑定，使作品具备直接演示的条件。整个过程体现了从问题出发、经由技术建模，再到产品化呈现的完整开发思路。

在演示效果方面，当前项目已经可以支持多类典型场景。比如，当用户提问“学校什么时候成立”“万柳北校区有哪些特点”“学校为什么强调跨龄教育”等问题时，系统能够从本地校园知识库中检索相关内容，并输出较自然、较适合学生阅读的答案。又如，当用户输入“中关村三小”“足球比赛”等关键词时，系统能够返回与主题相关的 B 站视频结果卡片，帮助用户进一步了解相关活动或传播内容。这些能力虽然看起来界面简洁，但背后已经包含了文档预处理、知识向量化、检索排序、模型生成、结果展示和缓存管理等多个环节。对于评审而言，这说明项目并非停留在概念验证，而是已经形成较完整、可运行、可展示的人工智能应用作品。

本项目的创新点可以概括为四个方面。第一，场景创新。项目并未追求做一个“大而全”的泛化聊天系统，而是明确聚焦校园知识讲解这一真实问题，以中关村第三小学的校史与校园文化内容为服务对象，体现了问题导向与教育场景意识。第二，检索方法创新。项目不是单纯使用向量搜索，而是将 Markdown 层级解析、语义分块、FAISS 粗检索、重排序、章节回溯聚合组合为一套完整流程，有效提升回答的相关性与连贯性。第三，交互方式创新。项目把文字问答和视频检索结合起来，形成“本地可信知识 + 外部公开资源”的复合型学习入口。第四，工程实现创新。项目采用模块化分层架构，使配置管理、模型调用、知识检索、缓存和 UI 展示相互解耦，既保证了当前功能可运行，也为今后扩展其他校园应用保留了空间。

从可行性和实用价值来看，本项目具有较明显的优势。首先，部署门槛相对较低。项目依赖 Python、Gradio、DashScope、FAISS 和 `yt-dlp` 等常见组件，不需要在本地部署大模型，具备较好的演示可行性。其次，知识来源更可控。与直接让通用大模型自由回答相比，本项目通过本地校园知识库对回答内容进行约束，更适合校园场景中的知识传播。再次，交互形式更贴近学生使用习惯。学生只需要输入自然语言问题即可获得回答，不必先掌握复杂检索技巧。最后，项目具备较好的扩展潜力。当前架构已经预留了图像生成、图生视频等模型配置项，后续如需拓展宣传展示、校园文创、课程活动讲解等能力，可以在现有框架基础上继续开发。

当然，项目目前也存在一些需要如实说明的边界与不足。第一，当前代码中实际使用的默认对话模型配置为 `qwen-flash`，虽然整体仍属于通义千问系列能力范围，但与早期方案文档中设想的具体型号并不完全一致，因此正式说明中不应把未统一落地的模型型号写成既定事实。第二，图像生成与图生视频能力虽然在配置中已经预留了模型参数和开关，但当前版本尚未在 `Orchestrator` 和前端界面中形成完整调用链，因此不能作为“已完成核心功能”来表述，更适合写成“后续扩展方向”。第三，当前参考来源展示机制在代码中已有事件流支持，但默认并未开启展示，因此在评审材料中只能写为“系统具备可扩展的来源展示机制”，而不宜写成默认常态能力。第四，当前测试主要集中在 RAG 相关流程的集成验证，尚未形成覆盖 UI、缓存、异常分支和外部检索链路的完整测试体系。

后续优化方向也已经比较明确。一是继续扩充校园知识库的数据类型，不仅覆盖校史与办学介绍，还可以纳入课程活动、校园通知、展馆内容、校园地图等更多知识源。二是完善回答来源展示与可追溯机制，增强答案的可信度和解释性。三是增强多轮对话与角色化交互体验，使系统不仅能回答单个问题，还能围绕同一主题进行连续讲解。四是逐步把已经预留的图像生成、图生视频等能力真正接入业务流程，形成更丰富的多模态校园展示作品。五是补充更系统的自动化测试与效果评估，让项目从“可演示”进一步走向“可持续迭代”。

综合来看，中关村三小校园智能讲解助手并不是把现成模型简单拼接到页面上的展示作品，而是一项从真实问题出发，经过资料整理、知识建模、检索设计、模型编排和界面落地逐步完成的人工智能应用项目。它面向学校教育场景，强调知识的准确性、表达的友好性和系统的工程可行性，已经具备较完整的问答与辅助检索能力，同时也保留了进一步发展的空间。作为人工智能（编程）作品，它体现了学生对人工智能技术在真实场景中应用方式的理解，也体现了将技术能力转化为具体产品形态的实践探索。

作品名称建议表述为“中关村三小校园智能讲解助手”或“基于大模型与知识库检索的校园智能讲解系统”。作品摘要可概括为：本项目围绕校园知识传播场景，构建了一套基于本地知识库、向量检索、重排序和大模型生成的智能讲解系统，可实现校史与校园知识问答，并提供相关视频信息检索辅助展示，具有创新性、智能性、可行性和较好的应用价值。

构思形成可表述为：在整理学校校史和校园资料时，我们发现信息内容虽然丰富，但分散在不同文档中，学生查找效率较低，且传统资料不够贴近儿童理解方式。因此，我们想到借助人工智能技术，将校园知识整理为本地知识库，并结合大模型问答能力，设计一个能够与学生自然对话的校园智能讲解助手。

设计过程可表述为：首先整理学校校史、校区介绍、课程活动等资料，转为结构化 Markdown 文档；然后设计文档分层切分与向量索引流程，构建本地知识库；接着实现基于 FAISS 的粗检索和基于重排序模型的精排，再将相关章节内容提供给对话模型生成答案；最后通过 Gradio 完成界面设计，并补充 B 站视频检索和缓存功能，使系统具备完整演示能力。

演示效果可表述为：系统支持用户输入校园相关问题，并从知识库中检索信息生成自然语言回答；回答过程可流式展示，交互较为自然；同时支持按关键词搜索与学校主题相关的视频信息，并将结果以卡片形式展示，增强了知识传播的直观性。

优点可表述为：本项目聚焦真实校园场景，目标明确；回答建立在本地知识库基础上，内容相对可控；系统采用分层架构，便于维护与扩展；界面轻量、部署方便，适合学校展示和课堂活动应用。

还需进一步研究的问题可表述为：未来还需要继续扩充知识库内容，提升回答来源展示与可追溯能力，完善多轮对话体验，并逐步将图像生成、视频生成等多模态能力真正接入系统主流程，同时加强测试与效果评估机制。
